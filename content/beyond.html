Subagents: divide independent work

Subagents are additional agent sessions assigned bounded tasks. For a larger project, one could inspect accessibility while another analyzes a failing check. Coordination and review still belong to the main task. They inherit permissions and can make mistakes.

Use two subagents for read-only reviews: one for counter logic, one for keyboard accessibility. Wait for both, reconcile disagreements, and summarize evidence. Do not edit files.

Availability and controls depend on client/version. CLI /subagents inspects agent threads where supported. For our tiny counter, a single agent is usually simpler. Subagents ↗

Git worktrees: separate checkouts

A worktree is another checkout of a Git repository with its own working files. It helps keep parallel experiments apart while sharing Git history. It does not automatically merge results or copy every uncommitted edit.

Desktop worktree controls are documented separately from terminal commands. First learn branches, commits and merge review; then use worktrees for two independent feature experiments. Verify which folder each agent is editing. Worktree orientation ↗

Hooks: actions at lifecycle events

Hooks can run scripts or MCP tools at points in the agent workflow, such as after tool use or when a turn stops. They can enforce a useful check, but introduce executable configuration and failure behavior to understand.

Current CLI provides /hooks for inspection and trust review. Read hook definitions before trusting them, especially from an unfamiliar repository. A hook is not automatically proof that validation succeeded. Hooks and trust ↗

Non-interactive runs

codex exec accepts a task from a shell without opening the interactive conversation UI. It is useful in scripts or continuous integration (CI), where a service runs repeatable checks. Configure access deliberately and capture failures.

codex exec --sandbox read-only "Summarize the counter architecture without editing files."

This is an example invocation, not an execution transcript. It needs installed Codex and authentication. Inspect exit results and the produced answer; unattended runs cannot rely on you answering every permission prompt. Automate a workflow only after it works reliably with human review. Model and reasoning-effort selection

A model is the system producing responses; reasoning effort is a supported setting that changes how much processing it can allocate. Use CLI /model to see what your account and client offer. More effort can cost time and usage without fixing a vague requirement.

Start with the available default, compare results on a real check, and change only when there is a reason. Avoid memorizing a model list or assuming unlimited usage. Current model control ↗ · Current model information ↗
