Useful context beats a long prompt

A good request makes four things easy to find: the goal, relevant context, constraints and completion criteria. Context means the information needed to interpret the task: files, errors, decisions and examples. More text helps only if it removes uncertainty.

Official prompting guidance ↗

Weak → useful → appropriately scoped

Fix the counter.

This leaves the bug, files and intended behavior open to interpretation.

The counter goes negative. Fix it so it stays at zero.

Now the behavior is clear, but scope and checks still need definition.

In app.js, prevent the count from dropping below 0. Keep increment and Reset behavior unchanged. Use plain JavaScript and no new dependencies. Verify 0 → minus → 0, 1 → minus → 0, and repeated minus clicks. Report any browser checks you could not run.

This says what to change and what to preserve, and turns “works” into examples. It does not dictate an implementation prematurely. A likely fix clamps the count or guards decrement. Verify both the state and visible number; changing only the display can hide a negative state.

Six realistic request patterns

Type these natural-language examples in the CLI composer. Replace files and checks with ones that exist in your project.

Understand code
Read app.js without changing it. Trace one + click from event listener to state update to screen update. Point out any assumption you cannot confirm.

Success: you can locate each step yourself. If it names a nonexistent file, stop and supply the correct path.

Fix a bug
After +, +, Reset, + the display should be 1, but I see 3. Reproduce or trace this sequence, fix the underlying state bug, and keep styling unchanged.

Success: the sequence passes after reload. If not, include console errors and actual versus expected numbers.

Add a feature
Add a step size of 2 to the counter, with a clearly labelled control. Keep the default step at 1. Before editing, propose how decrement should behave near zero and wait for my decision.

Success: the boundary decision is explicit before code changes. Check both step sizes and Reset afterward.

Debug a failing check
node check.mjs fails on the repeated decrement case in the completed project. Read the failure and relevant logic before changing code. Explain whether the implementation or check is wrong, then fix only the cause.

Use this only in a folder containing the supplied check.mjs. Success: the failure disappears for the right reason, not because an assertion was removed.

Review changes
Review this counter diff for behavior and keyboard accessibility. Do not edit. Prioritize defects with a reproducible sequence, file reference and expected result. Say what you did not test.

A second review is useful, but manually exercise the suspected bug before accepting the claim.

Refactor
Reduce duplicate display-update code in app.js without changing behavior or adding dependencies. Keep the public functions used by check.mjs. Run the existing check and list any manual checks still needed.

Success: behavior stays the same and the diff is understandable. If scope expands into a framework migration, narrow it immediately.
