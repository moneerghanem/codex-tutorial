Plan when decisions matter

A one-handler Reset fix rarely needs a formal plan. A counter with persistence, undo and configurable step sizes introduces interactions worth discussing first. Planning helps reveal assumptions; it does not make the eventual code correct.

In CLI, /plan opens Plan mode. Use its interface to review the plan before implementation. CLI command source ↗

Plan a counter step-size control. Do not edit yet. Identify the files, boundary decisions at zero, and a short verification checklist. Keep the existing Reset behavior.

Likely result: proposed steps and questions. Verify that the plan includes the zero boundary and avoids unnecessary infrastructure. If it proposes a server, explain that the project is intentionally static.

Review the plan like a specification

  • Does it solve your actual problem?
  • Are assumptions labelled and acceptable?
  • Does each changed file have a purpose?
  • Are checks executable in your environment?
  • Is there a smaller step you can validate first?
Revise the plan: no persistence or backend. Clamp decrement to zero when the step is larger than the current count. Keep the default step at 1. Implement only after reflecting those decisions.

A good correction changes the requirement, not just the tone. Do not approve a plan you cannot explain in your own words. Planning guidance ↗

Steer active work precisely

CLI: current documentation distinguishes Enter (send instructions into active work) from Tab (queue for the next turn). Custom keymaps and older releases can differ; inspect the current shortcut help. Avoid assuming a queued correction has already taken effect.

Stop expanding scope. Keep the three existing buttons and fix only Reset. Before continuing, tell me which files you have already changed.

If a command is currently running, a correction is not proof that it stopped. Inspect tool output and the diff. In an IDE or desktop app, use that interface’s composer and stop controls; CLI bindings do not automatically apply.
