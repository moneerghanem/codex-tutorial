Lesson 03 / 20–30 min estimate

Your first successful task

Understand a project, fix Reset, prove it works.

Prerequisites: Codex installed; complete Get it running

One project. One fix. Real evidence.

We will inspect a tiny webpage, fix a broken Reset button and verify the result. Use the starter download. Its Reset and lower-bound behavior are deliberately wrong. The completed version is a comparison solution; keep it in a separate folder.

No backend, API key for the webpage, database or framework is needed. A dependency is another program or library a project needs; this practice webpage has no external dependencies. Codex still needs your own eligible access.

Guided first-task walkthrough

Follow these steps in your own project. The controls track your place; they do not run Codex or inspect your files.

  1. Extract the starter and open index.html in a browser.
  2. Start Codex from the extracted folder.
  3. Ask for a read-only explanation.
  4. Ask for the Reset fix.
  5. Inspect the diff.
  6. Reload and manually verify.

First, ask it to read

Goal: build a mental picture before allowing edits. Where: the Codex CLI prompt, after you started codex in counter-starter.

Explain this counter project without editing files or running installation commands. Read index.html, style.css and app.js. Describe the button event handlers and identify how Reset currently behaves. Cite the relevant code.

The scope prevents an explanation request from becoming a redesign. Likely result: a short description with references to the three files. Verify the explanation by opening app.js in your editor and locating the Reset handler yourself. If it discusses a React component, correct the folder or file assumption immediately.

If the explanation is vague or wrong
This is a plain JavaScript webpage. Read app.js in the current directory and point to the Reset event listener. Do not edit anything. Explain what happens after three increments and then Reset.

Then request the smallest useful change

Open index.html directly in a browser. Click + three times, then Reset. In the starter, Reset leaves the number unchanged. Now ask:

Fix Reset in app.js so it sets the count to 0 and updates the displayed number. Keep the existing HTML/CSS and +/− behavior unchanged for this task. Report the changed lines and checks you actually ran. If you cannot interact with a browser, say so and give me manual checks.

These completion criteria define observable success and postpone the negative-number bug to the next exercise. In the supplied starter, a shared event listener calls CounterModel.nextCount; its reset branch returns the old count. A focused solution returns zero from that branch while keeping the existing render call. No exact response or edit is guaranteed.

Read the change, then try it

A diff compares versions of a file. Inside the CLI, enter /diff. Look for the Reset transition returning zero and the existing event handler rendering that result; investigate unrelated changes. If the project is not tracked by Git, use your editor to compare against a saved copy or initialize a checkpoint as described in Review and verify.

  1. Reload the webpage so it uses the new JavaScript.
  2. Click + three times: expect 3.
  3. Click Reset: expect 0.
  4. Click Reset again: expect 0, with no error.
  5. Click + once after Reset: expect 1.

If the display resets but the next + jumps to 4, the agent may have changed the text without resetting the state variable. Report that exact sequence and ask it to fix the state, not only the display. Save your reviewed result before continuing to the remaining exercises.

What remains unverified?

Reset passing does not prove the lower-bound rule, keyboard access or all browsers. Keep those as separate checks.
